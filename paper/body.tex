\abstract
% context
{Astronomical archives answer positional queries from relational databases, and in the
PostgreSQL world two extensions dominate: Q3C, which keys each source by an integer
drawn from a quad-tree on a cube and stores it in a B-tree, and pgSphere, which stores
spherical geometry in a GiST tree. The first is compact and fast for points; the second
is general and indexes regions as well.}
% aims
{We ask whether the two can be combined: a single index that keeps the integer key and
the B-tree, yet answers cones, polygons, cross-matches and stored footprints in
archives' own geometry language, establishing where it helps, where it does not, and
what its cost model depends on.}
% methods
{We present \texttt{skycell}, a PostgreSQL extension that keys positions by their
order-29 HEALPix cell in the nested scheme and turns a query region into index ranges.
How finely to cut is decided by a cost model -- the price of an extra index range
against the rows it removes -- with the local source density read from the histogram
\texttt{ANALYZE} already keeps for the key column. Cells are classified conservatively
against the region, and a planner support function rewrites the predicate into B-tree
range conditions plus an exact test. Coverings are validated by brute force against
millions of catalogue points, including adversarial cones and polygons. Performance is
measured against Q3C 2.0.5 and pgSphere 1.5.2 on two 10-million-row corpora -- one
synthetic, one resampled from the real Gaia DR3 density field -- in trials where all
three methods answer the same query back to back in a randomized order, analysed
paired, warm and with caches dropped, and repeated on a 50-million-row catalogue where
pgSphere's index no longer fits in memory.}
% results
{Warm, skycell is faster than pgSphere by 6--11\% for cone radii of 1\arcsec--1\arcmin\
and by 31--37\% at 3\degr, indistinguishable between 6\arcmin\ and 1\degr; cold it is
faster at every radius on both corpora (ratios 0.39--0.95). It keeps an index of
214\,MB against pgSphere's 685\,MB -- 22.5 bytes per row against 72, which at Gaia
DR3's $1.8\times10^9$ sources is 38\,GiB against the 160\,GiB the pgSphere-plus-Q3C pair
needs to cover both cone searches and cross-matching, builds in 1.4\,s against 42\,s,
answers convex polygons 2.7--4.4 times faster, matches \texttt{q3c\_join} on
cross-matching while being 2.5--3.3 times faster than pgSphere at it, and its row
estimates are wrong by a factor 1.2 rather than 2.5--3.0. The cost model's one
parameter is derived from the relation's own statistics rather than configured, its
chosen cell order costs about 3\% against the best available one, and its density
estimate is accurate to about 25\% on ordinary sky. Raising the catalogue to 50 million
rows widens the advantage for regions of 30\arcmin\ and larger (at 1\degr, 0.85 to 0.60
warm, 0.53 to 0.31 cold) while cones of an arcminute and below do not move. An
ObsCore-shaped relation measured at three sizes puts the crossover with pgSphere between
0.5 and 2 million rows for degree-scale cones, and beyond 10 million for small cones on
field-clustered data.}
% conclusions
{A cost-based covering over an equal-area integer key is a sound basis for a sky index,
and the right question is not whether it is faster but for which queries. Its cost is
paid per query and its benefit per row scanned, so it wins where enough rows are scanned
to amortise a covering -- degree-scale regions, polygons, cross-matching, cold caches --
and that boundary moves up in radius as the catalogue grows denser. On a Gaia-sized
catalogue a small cone search is not the workload this index improves.}

\section{Introduction}

Almost every question asked of an astronomical archive is positional: what is within
this cone, which observations cover this field, which of my sources match that
catalogue. In the Virtual Observatory these questions arrive as ADQL \citep{adql}
through the Table Access Protocol \citep{tap}, and the service has to turn them into
something a relational database can answer with an index.

Two PostgreSQL extensions carry most of this traffic. Q3C \citep{q3c} projects the
sphere onto a cube, subdivides each face with a quad-tree, and numbers the cells along a
space-filling curve, so each source is one 64-bit integer in a B-tree and the table can
be sorted along the same curve. pgSphere \citep{pgsphere} takes the other route: it adds
spherical types -- points, circles, polygons, boxes -- and indexes them with GiST over
bounding volumes, so regions can be stored and queried as data, not only as query
arguments.

The scale this has to work at is set by archives already in operation. The ESA Gaia
Archive \citep{gaiaarchive1, gaiaarchive2} serves order $10^9$ sources through an
extended TAP interface, and its published description puts cross-match -- matching a
user's uploaded positions against the catalogue -- among its server-side capabilities,
so Sect.~\ref{sec:xmatch} treats it as a first-class result rather than an afterthought.

Neither idea is new to astronomy: the Hierarchical Triangular Mesh \citep{htm} already
keyed positions by a subdivided polyhedron, and the zones algorithm \citep{zones} showed
how far a purely relational arrangement can be pushed for cross-matching. What has
changed is the size of the catalogues and the fact that most queries now arrive through a
generated layer \citep[e.g.][]{dachs} rather than being written by hand.

The two designs trade off against each other. A linear key in a B-tree is compact, cheap
to probe and orders the heap, but a region has to be turned into a set of key ranges
before the index can be used, and that approximation's quality depends on how finely the
region is cut. A tree of bounding volumes has no such step and handles extended objects
naturally, but its keys are larger, its nodes overlap, and it imposes no useful order on
the table.

This paper presents \texttt{skycell}, which keeps the integer key and asks a cost
question at the point where the classical approach fixes a constant: how finely should a
region be cut? The answer depends on two quantities the database already knows -- how
many sources sit in that part of the sky, and how much an extra index range costs -- and
can be computed rather than configured.

Because the claims here are quantitative, the measurements are built to survive scrutiny
rather than to flatter the method: every query is answered by all three methods back to
back in a randomized order, repeated and analysed paired; everything is measured both
warm and with the page cache dropped; and everything is repeated on a second corpus whose
density structure comes from the real Gaia DR3 sky rather than from the authors.
Section~\ref{sec:method} develops the method, Sect.~\ref{sec:impl} its planner
integration, Sect.~\ref{sec:validation} what is proven versus tested,
Sect.~\ref{sec:bench} the benchmark protocol, Sect.~\ref{sec:results} the results, and
Sect.~\ref{sec:tap} a TAP service and the measured crossover;
Sect.~\ref{sec:discussion} states plainly what these measurements do not establish.

\section{Method}
\label{sec:method}

\subsection{An equal-area integer key}
\label{sec:key}

A position is keyed by the index of the HEALPix cell containing it at order 29 in the
nested scheme \citep{healpix} ($12\cdot4^{29}\approx1.4\times10^{19}$ cells of about
0.4\,mas), computed by the standard \texttt{ang2pix\_nest} arithmetic and stored as a
signed 64-bit integer -- the plain nested index at a fixed order, not a multi-order
key, so a key is directly comparable with another and a B-tree orders them along the
HEALPix curve. Three properties follow, and only the first is shared with Q3C's cube
quad-tree.

Cells are \emph{nested}: the order-29 descendants of a cell $p$ at order $k$ are exactly
the contiguous interval
\begin{equation}
  \bigl[\, p\cdot 4^{\,29-k},\; (p+1)\cdot 4^{\,29-k} - 1 \,\bigr],
  \label{eq:interval}
\end{equation}
so a region covered by cells of any orders becomes a union of integer intervals and a
B-tree can answer it with range scans. The \texttt{NUNIQ} encoding of the MOC standard
\citep{moc}, used here for stored regions (Sect.~\ref{sec:moc}), packs the order into
the key as $4\cdot4^{k} + p$; the two are related by Eq.~(\ref{eq:interval}), and
\texttt{skycell} converts between them rather than storing two representations.

Cells are \emph{equal area}, so a count of keys in an interval divided by its length in
cells is proportional to a source density per unit solid angle: the histogram
\texttt{ANALYZE} already keeps for the key column is therefore a crowding map
(Sect.~\ref{sec:density}) with no extra statistics machinery. And cells are
\emph{standard} -- the same numbering underlies Gaia's \texttt{source\_id} \citep{gaia}
and IVOA Multi-Order Coverage maps \citep{moc} -- so keys, coverings and stored
footprints are interoperable rather than private to one extension.

\subsection{Coverings decided by cost}
\label{sec:cost}

A query region is covered by cells whose union contains it; the covering becomes range
conditions on the key, and rows inside the covering but outside the region are removed
by an exact test. Cutting finer means fewer such false positives and more ranges. With
cells of size $s$ covering a region of characteristic radius $r$ and a local source
density $\rho$,

\begin{equation}
  C(s) = n_{\rm ranges}(s)\,c_{\rm range} + \rho\,\bigl(A_{\rm cover}(s) - A_{\rm region}\bigr).
  \label{eq:cost}
\end{equation}

Both terms are in rows: the second is the expected number of false positives, and
$c_{\rm range}$ converts one additional index range into the number of false-positive
rows it is worth avoiding -- a property of the installation, not of the sky (the ratio
between the cost of opening one more B-tree range scan and of fetching and discarding
one heap row; Sect.~\ref{sec:calib} measures it).

A covering follows the region's boundary, so for $s \ll r$ the number of ranges grows as
$r/s$ -- the curve enters and leaves the region once per boundary crossing, and the
number of such clusters is the classical measure of a space-filling curve's quality
\citep{hilbert} -- while the wasted area grows as the perimeter times $s$. Writing
$A_{\rm cover} \simeq \pi(r + \beta s)^2$ and $n_{\rm ranges} \simeq \gamma r/s$ and
minimising Eq.~(\ref{eq:cost}) gives

\begin{equation}
  s_\star = \sqrt{\frac{\gamma\,c_{\rm range}}{2\pi\beta\,\rho}},
  \label{eq:sstar}
\end{equation}

which does not depend on the size of the region: the density of the sky and the price
of a range decide how finely it is worth cutting. For $s \gtrsim r$ the covering is a
handful of cells and the balance differs, so rather than solve the branches the
implementation evaluates Eq.~(\ref{eq:cost}) at all 30 orders -- a few floating-point
operations each -- and takes the cheapest, which also lets a cap on the number of
ranges and a guard on cell size simply remove candidates. The constants
$\beta = 0.7$ and $\gamma = 2$ are geometric; Sect.~\ref{sec:calib} shows the choice of
order is flat enough near its optimum that they do not need to be exact.

Figure~\ref{fig:covering} shows the two extremes on the same cone radius: at high
Galactic latitude the covering is a single range of large cells covering 5.6 times the
cone's area, because there is almost nothing to exclude; in the bulge the same cone is
covered by 23 cells in 8 ranges covering 1.3 times its area, because there the rows
removed are worth the extra ranges.

Two guards keep the model safe against its own inputs: a partly covered cell is never
allowed to exceed a multiple (64 by default) of the region's own area, bounding the
damage from a dense cluster the histogram underestimates; and gaps between ranges are
merged when the rows they contain cost less than the range they save.

\paragraph{The density estimate.}
\label{sec:density}
PostgreSQL's \texttt{ANALYZE} stores, for the indexed expression, an equi-depth
histogram: a sorted list of $B+1$ bounds $h_0 < h_1 < \dots < h_B$ in key space such
that each bucket $[h_{i}, h_{i+1})$ holds about $N/B$ of the table's $N$ rows. Because
the key is an equal-area cell index, the rows in a key interval $[a,b]$ are estimated
by linear interpolation within the buckets it spans,
\begin{equation}
  \hat{n}(a,b) = \frac{N}{B}\sum_{i} \frac{\bigl|[a,b] \cap [h_i, h_{i+1})\bigr|}{h_{i+1}-h_i},
  \label{eq:hist}
\end{equation}
and the corresponding density in rows per steradian is
\begin{equation}
  \hat{\rho}(a,b) = \frac{\hat{n}(a,b)}{(b-a+1)\,A_{29}} .
  \label{eq:rho}
\end{equation}
The estimate used by Eq.~(\ref{eq:sstar}) is $\hat{\rho}$ evaluated over the order-$m$
cell containing the region's centre, with $m$ chosen so that $s_m \approx 4r$: large
enough to contain enough rows to be a density, small enough to be local.

Three caveats. The quantity is a density per unit solid angle, not a selectivity --
PostgreSQL computes the planner's own selectivity for the rewritten range conditions
separately, from the same histogram. Equation~(\ref{eq:hist}) assumes rows are spread
uniformly inside a bucket, which fails for a cluster smaller than one -- hence the area
guard of Sect.~\ref{sec:cost}. And the estimate is only as local as a bucket: with
$B=1000$ and $N=10^7$ a bucket holds $10^4$ rows, so below that scale
Eq.~(\ref{eq:rho}) averages over a $10^4$-row region, the right answer to a different
question. Section~\ref{sec:estimator} measures how close $\hat\rho$ lands to the truth.

\paragraph{Classifying cells: what is bounded and what is not.}
\label{sec:classify}
A cell must be classified against the region as inside, outside or straddling its
boundary, and the three outcomes are not symmetric: a cell called \emph{outside} is
dropped, so if that is ever wrong the query silently loses rows, while \emph{inside} and
\emph{straddling} cells both produce a superset the exact predicate (Sect.~\ref{sec:impl})
trims back. Only the outside decision therefore needs a bound rather than an estimate.

The bound used is
\begin{equation}
  R_{\rm cell}(k,p) = \min\bigl(\mathrm{maxpixrad}(k),\;
    \max_{i}\, \angle(\mathbf{c}_{k,p}, \mathbf{v}_i)\bigr),
  \label{eq:rcell}
\end{equation}
where $\mathbf{c}_{k,p}$ is the cell's centre and $\mathbf{v}_i$ its four corners.
The first term is the analytic worst case over the sphere used by the reference HEALPix
implementation; the second is the cell's own extent, which is smaller for most cells.
A cell is outside when $\angle(\mathbf{q}, \mathbf{c}_{k,p}) - R_{\rm cell} >
r + \epsilon$ for a cone of centre $\mathbf{q}$ and radius $r$, and correspondingly for
each of a polygon's bounding half-spaces. The margin
$\epsilon = 2\times10^{-13}$\,rad (40\,pas) covers the accumulated floating-point error
of the handful of dot products, cross products and inverse trigonometric calls
involved, each carrying a few units in the last place; it is five orders of magnitude
below the 0.4\,mas resolution of an order-29 cell, so it costs nothing.

The inside test may be, and is, tighter: it uses the distances from the query centre to
the cell's own corners and edge midpoints directly. A tempting alternative for the
outside test -- distance to the chords between corners, inflated by the edge's departure
from its chord at the midpoint -- is not a bound: near where an edge crosses its chord
plane that departure collapses towards zero while the true one does not, by a factor
reaching 64 at order 18, causing an error of $\sim$$10^{-8}$\,rad invisible to every test
we had. Eq.~(\ref{eq:rcell}) avoids it, at a cost of 2.5\% more index ranges and no
measurable time.

\paragraph{Regions as stored objects.}
\label{sec:moc}
A footprint is covered by a small number of cells written in the \texttt{NUNIQ} encoding
of the MOC standard and stored one per row in an ordinary B-tree. The footprints
containing a given position are those whose cell is one of that position's ancestors, a
short list of equality lookups (no duplicate elimination needed, since a MOC's cells are
disjoint by construction); refinement stops when cells become negligible next to the
region, keeping the ancestor list short.

\texttt{skyregion} is one type internally tagged by kind rather than a family of
per-shape types, so a single footprint column can hold circles and polygons together --
an ObsCore \texttt{s\_region} column, for instance, mixes the single-pointing circles of
simple exposures with the polygons of non-trivial footprints in the same rows, covered
by one function, \texttt{skycell\_region\_moc}, regardless of which kind a row holds.
pgSphere has no equivalent: \texttt{scircle} and \texttt{spoly} are separate types, so a
mixed-shape column needs two columns, or a view over both, in its place.

\subsection{The query surface}

The extension exposes ADQL's own vocabulary: types \texttt{skypos} and
\texttt{skyregion} and functions \texttt{point}, \texttt{circle}, \texttt{box},
\texttt{polygon}, \texttt{contains}, \texttt{intersects}, \texttt{distance},
\texttt{area}, \texttt{coord1}, \texttt{coord2} and \texttt{centroid}, so that a
translator emits the standard's spelling rather than a dialect; the operator form
\texttt{pos <@ circle(\ldots)} is the one a planner can answer from an index, and the
function form returns the same rows.

\texttt{skyregion}'s text representation is a second point of contact with the
standard: it is IVOA STC-S \citep{stc} -- \texttt{CIRCLE ICRS $\alpha$ $\delta$ $r$} /
\texttt{POLYGON ICRS $\alpha_1$ $\delta_1$ \ldots}, whitespace-separated -- the same
syntax an ObsCore \texttt{s\_region} column already carries, so an
\texttt{s\_region skyregion} column casts directly from, and prints back as, the
archive's own STC-S text with no translation step; a stray flavor/refpos token some
archives emit (\texttt{TOPOCENTER}) is accepted and discarded, and a non-ICRS frame is
refused with an error rather than silently mis-read. This is independent of the
query-time translation of ADQL's \texttt{CIRCLE(\ldots)}/\texttt{POLYGON(\ldots)} inside
a query (Table~\ref{tab:ops}): STC-S is only the text form the stored value takes.

For hand-written SQL migrating from Q3C, \texttt{skycell\_radial\_query} and
\texttt{skycell\_join} take Q3C's own argument lists as a prefix replacement, both
reducing to the canonical \texttt{skycell\_cone}, which serves the cone search and the
cross-match with one predicate since the only difference is whether the centre is a
constant.

Archives also need the astrometry deciding \emph{where} a source is at the epoch asked
about. \texttt{skycell} implements the IVOA UDF registry's names (\texttt{ivo\_epoch\_prop},
\texttt{ivo\_epoch\_prop\_pos}, \texttt{ivo\_apply\_pm}, \texttt{ivo\_healpix\_index},
\texttt{ivo\_healpix\_center}) with the rigorous epoch propagation of the Hipparcos
catalogue \citep{hipparcos}, plus ICRS/Galactic/ecliptic frame conversions; a
proper-motion-aware cone search is then an indexable cone widened by the largest motion
of interest, intersected with an exact test on the propagated position. These are
exercised by round-trip and published-value tests (epoch propagation returns Barnard's
star to sub-microarcsecond over a 16-year round
trip) rather than benchmarked, so no performance claim is made for them.

Table~\ref{tab:ops} sets the three side by side for the constructs where they differ
most. The right-hand column is mostly the identity, which is the point of adopting the
standard's spellings; the middle column is where the work goes, and two of its rows have
no direct form at all -- the remaining ADQL surface (\texttt{BOX}, \texttt{DISTANCE},
\texttt{COORD1}/\texttt{COORD2}, epoch propagation) translates the same way and is
omitted for space.

\section{Implementation}
\label{sec:impl}

The extension is written in C against the PostgreSQL 15+ server API: a geometry layer
with no database dependencies (HEALPix arithmetic, region predicates, the covering) and
a layer that connects it to the planner via a \emph{planner support function}
(\texttt{SupportRequestSimplify}, the mechanism PostGIS uses for \texttt{ST\_DWithin}).
Before path generation, a predicate such as
\texttt{point('ICRS', ra, dec) <@ circle('ICRS', $\alpha$, $\delta$, $r$)} is replaced by
a disjunction of range conditions on the key expression, conjoined with the exact test:

\begin{quote}\small\ttfamily
(cell BETWEEN lo1 AND hi1\\
 OR cell BETWEEN lo2 AND hi2 OR ...)\\
AND skycell\_in\_region(point(ra, dec),\\
\hspace*{6em}circle(...), 0.29)
\end{quote}

The support function builds this candidate expression from the predicate's position
argument and keeps it only if the relation carries an index on it, so the same query
text works whether positions are two columns or a \texttt{skypos} column. The index
conditions are then ordinary range predicates, so the planner estimates their
selectivity from the same histogram, and the exact test's last argument carries the
covering's occupied fraction, keeping the product of the two estimates close to the
truth.

Two caches matter for planning cost: the density model and matching-index identity, per
backend, dropped on statistics/relation changes; and coverings, memoised by region and
statistics source, since a service plans the same cone many times. Measured on a TAP
corpus, these are worth 45--70 and up to 50\,\textmu s per plan respectively.

For joins, where the region is not a constant, the rewrite emits a fixed number of range
slots per outer row (the structure \texttt{q3c\_join} uses), while
\texttt{skycell\_cone\_ranges()} offers a variable number through a \texttt{LATERAL}
join -- a difference in plan shape that Sect.~\ref{sec:xmatch} shows matters.

\paragraph{Ingestion and maintenance.} The index is an ordinary B-tree on an expression:
an insert adds one 8-byte key, non-moving updates don't touch it, and there is no
method-specific rebalancing. Bulk ingestion benefits from loading in key order, the same
order the queries exploit; and because the covering depends on the histogram, statistics
matter more than for a GiST index -- the area guard of Sect.~\ref{sec:cost} bounds the
damage from a stale one, and \texttt{ANALYZE} on the 10-million-row corpora here takes
0.5--1.4\,s.

\section{What is proven, and what is tested}
\label{sec:validation}

\begin{quote}
\textbf{Proposition.} Let $R$ be a cone or convex polygon and let $\mathcal{C}$ be the
covering computed for it. If (i) every point of a HEALPix cell at order $k$ lies within
$\mathrm{maxpixrad}(k)$ of that cell's centre, and (ii) every angle computed by the
classification carries an absolute error below $\epsilon$, then every order-29 cell that
intersects $R$ lies in one of the ranges of $\mathcal{C}$.
\end{quote}

\emph{Proof sketch.} The covering is produced by a descent that starts from cells whose
union is the whole sphere and, at each step, either keeps a cell, drops it, or replaces
it by its four children, whose union is the parent. The union of the kept cells is
therefore reduced only where a cell is dropped, which happens only when it is classified
outside. Taking $R_{\rm cell} = \mathrm{maxpixrad}(k)$ in Eq.~(\ref{eq:rcell}), every
point $\mathbf{x}$ of cell $(k,p)$ satisfies
$\angle(\mathbf{x},\mathbf{c}_{k,p}) \le R_{\rm cell}$ by (i); hence if
$\angle(\mathbf{q},\mathbf{c}_{k,p}) - R_{\rm cell} > r + \epsilon$, then by the
triangle inequality on the sphere and (ii) every point of the cell is farther than $r$
from $\mathbf{q}$, so the cell does not intersect the cone. The polygon case is the same
argument applied to each bounding half-space. Truncation by the range cap, the area
guard or the step budget only stops refinement, which keeps a cell whole, so it cannot
remove a cell either. A cell containing a point of $R$ intersects $R$ and is therefore
never dropped. $\square$

The proposition is conditional. Condition (i) is a property of HEALPix, not of this
work: the reference implementation's $\mathrm{maxpixrad}$ is analytic, verified
numerically over $1.6\times10^6$ sampled boundary points at every order (largest observed
ratio 0.9999). The tighter corner term in Eq.~(\ref{eq:rcell}) additionally assumes the
distance extremum over a cell is at a corner -- supported by the same scan (ratio 0.96)
but not proven; \texttt{skycell.exact\_cells = off} rests the proposition on (i) alone, at
the cost of Sect.~\ref{sec:classify}. Condition (ii) is an assumption about
floating-point arithmetic, not a theorem: $\epsilon$ is chosen five orders of magnitude
above the plausible accumulated error and five below the leaf cell.

Because a covering that misses a cell silently loses rows, the implementation is also
checked by exhaustion. The HEALPix layer is checked against known cell centres, round
trips at all 30 orders, the nesting property of Eq.~(\ref{eq:interval}), equal area
($\chi^2/\nu=1.14$ over 768 base cells), and the bounds of Sect.~\ref{sec:classify}, over
$1.6\times10^6$ sampled points including the poles and zone boundaries. The covering is
checked against a 2-million-point clustered catalogue for cones from 1\arcsec\ to
120\degr\ and convex polygons; against 30\,000 adversarial cones (poles, zone boundary,
$\alpha=0$, face edges, radii 0.02\,mas--10\degr) with 200 points sampled inside each,
half within a part per billion of the rim; and against 7266 adversarial polygons at the
same places, with 866\,537 points drawn inside them. All assert zero false negatives --
this is the test that caught the error of Sect.~\ref{sec:classify}. At the SQL level, two
regression suites require every indexed answer to equal a sequential scan with the exact
predicate: 240 cones, 60 polygons, both join forms and the MOC lookup in the first; the
ADQL surface over 120 random regions, index-plan presence/absence, epoch-propagation and
frame conversions in the second.

\section{Benchmark}
\label{sec:bench}

\subsection{Three corpora}
\label{sec:corpora}

The \emph{designed} corpus is 10 million synthetic sources with a density contrast
resembling a real optical survey (35\% uniform, 45\% in a Galactic disk, 12\% in a
Gaussian bulge, 8\% in 200 clusters), drawn deterministically from a seed -- and
invites the objection that its density structure was chosen by the authors of the
method under test.

The \emph{Gaia} corpus removes that objection as far as we can: source counts from the
ESA Gaia archive for every order-9 HEALPix cell ($3\,145\,728$ cells of 0.11\degr,
summing to the published DR3 total $1\,811\,709\,771$) give 10 million positions placed
proportionally to each cell's count, uniformly within it. It carries the real sky's
crowding -- disk, bulge, Magellanic Clouds, scanning-law texture -- down to the
0.11\degr\ map scale, below which it is locally Poisson by construction; no real
positions are used, so it tests whether the cost model behaves the same on a density
field the authors did not invent.

The \emph{real} corpus removes the remaining objection: ten million real Gaia DR3
positions (\texttt{random\_index} $<10^7$, a precomputed random permutation, so a
uniform thinning that preserves two-point structure at every scale, not only above a map
cell), plus 1.6 million sources forming eight \emph{complete} fields at full density
($\omega$~Cen, 47~Tuc, M4, M13, Baade's Window, the Galactic centre, the LMC, and an
off-cluster control) since thinning dilutes crowding to 0.55\% of its true surface
density. We use it for the density-estimator and ablation measurements, where sub-cell
structure is the whole question, holding it twice -- once in cell order, once in
\texttt{random\_index} order (random on the sky) -- to measure physical layout as a
variable rather than a fixed condition (Sect.~\ref{sec:ablation}).

\subsection{Protocol}
\label{sec:protocol}

Q3C 2.0.5, pgSphere 1.5.2 and \texttt{skycell} each hold the same logical rows in their
own natural layout, all three physically ordered along a space-filling curve so that
heap locality is held equal (Table~\ref{tab:repro}). Queries are the documented
interface of each extension (\texttt{q3c\_radial\_query}, \texttt{spoint <@ scircle},
\texttt{skycell\_cone}), and row counts are compared on every query.

The measurement is organised as \emph{trials}: one query centre and radius, all three
methods answering it back to back in an order drawn at random for that trial (and
recorded, so an order effect can be measured rather than assumed away), repeated five
times with the query set traversed in a random order each time. The analysis is paired
-- median over repetitions per method, ratio between methods for that same query, so the
query's own difficulty cancels -- with a percentile bootstrap (4000 resamples) interval
over queries; a ratio is called a difference only when its interval excludes 1.

Everything is measured \emph{warm} (an untimed pass over the whole query set precedes
the measurement, so no method sees a colder cache than another) and \emph{cold} (server
restarted, its 2\,GB of shared buffers and the VM's page cache empty, only the first
repetition used). A separate randomized pass under \texttt{EXPLAIN (ANALYZE, BUFFERS)}
records planning time, execution time, buffer pages and the planner's row estimate
apart from each other.

Cone radii span 1\arcsec\ to 3\degr\ with 16--400 queries each, half the centres from
catalogue positions (density-weighted) and half uniform on the sky. Cross-matches join a
200\,000-row probe table (half catalogue sources displaced by $\sim$0.3\arcsec, half
uniform) to the catalogue; footprint queries ask which of 20\,000 stored circles contain
each of the 200\,000 probes.

\section{Results}
\label{sec:results}

All three methods return identical row counts on every query of the grid. In the
cross-matches pgSphere returns one or two more pairs out of $\sim$100\,000, consistent
with its $10^{-9}$\,rad comparison tolerance counting sources exactly on the rim.

\label{sec:phase}
That measurement matters more than it sounds: measuring one method's whole grid then the
next instead gives ratios of 0.69--0.87 below 30\arcmin\ where the paired protocol finds
0.89--1.03, since the phase-ordered arrangement flatters whichever method runs later --
here, \texttt{skycell}. The number above is the one we stand behind, and why every
comparison here is paired inside a trial.

Cold, the picture is more favourable: skycell is faster at every radius on both corpora,
by 5\% at 1\arcmin\ and by a factor 2--2.5 at 30\arcmin\ and beyond, because it touches a
third of pgSphere's buffer pages at 1\degr\ (55 against 154) -- a few microseconds of
memory traffic when those pages are warm, the whole cost of the query when they are not.

\label{sec:scope}
Against Q3C, \texttt{skycell} is faster by a factor 4--50, but that number carries three
different strengths. Against \texttt{q3c\_radial\_query} 2.0.5, which expands every call
into 100 key ranges regardless of radius (about 300 buffer pages and 1.2\,ms of planning
before any row is read), the factor 4--50 is a comparison of \emph{implementations}, and
we stand behind it. Against \texttt{q3c\_join}, which the Q3C authors intend for
cross-matching and does not carry that fixed expansion, the two are level
(Sect.~\ref{sec:xmatch}) -- the comparison informative about the two indexing
\emph{approaches}. About the cube quad-tree as a method we make no claim: a
covering-aware radial query in Q3C would plausibly close most of the cone gap. pgSphere
was used with its documented types and a GiST index at default settings, untuned
further; no method was given prepared statements or plan reuse, which would help
\texttt{skycell} most, since planning differs most between them. The order effect the
randomization controls is small but real (going first costs pgSphere 19\% and skycell
$-5$\% warm, Q3C flat), inflating the ratios' variance rather than biasing them.

\paragraph{Does the advantage grow with the catalogue?}
\label{sec:scale}
Ten million rows is 0.55\% of Gaia DR3, and the argument that an index matters most when
it does not fit in memory is an argument about scale, so we repeated the whole protocol
on a 50-million-row Gaia-density corpus. There, pgSphere's GiST index is 3442\,MB against
a 2\,GB \texttt{shared\_buffers} and no longer fits, while \texttt{skycell}'s 1072\,MB
B-tree still does.

The answer (Table~\ref{tab:scale}) divides by region size. For 30\arcmin\ and larger the
advantage grows markedly: at 1\degr\ the warm ratio improves from 0.85 to 0.60 and the
cold ratio from 0.53 to 0.31, because the buffer gap widens (152 against pgSphere's 514,
up from 55 against 154 at $10^7$ rows). For cones of an arcminute and below nothing
improves -- 1\arcsec\ stays at 0.89, 1\arcmin\ moves from 0.93 to 1.02 -- because both
methods touch five to seven pages whatever the table size, so what remains is
\texttt{skycell}'s planning (0.016--0.020\,ms against pgSphere's flat 0.009), which grows
with source density as a denser sky makes Eq.~(\ref{eq:sstar}) cut finer.

The rule that emerges is about pages rather than rows: \texttt{skycell} wins wherever a
query has enough pages to save, and the larger the catalogue the more that is worth. An
arcsecond cone on any catalogue is not the workload this index improves; a degree-scale
selection, a polygon or a cross-match on a large one is.

\subsection{Index size, build time, and what they cost at Gaia's scale}
\label{sec:scale-memory}

Index size and build time are operational numbers -- what an ingest, a restore or a
schema migration has to pay -- and the one result in this paper insensitive to protocol,
so it is worth carrying to the scale an archive runs at
(Table~\ref{tab:gaia}). The cost per row is flat between $10^7$ and $5\times10^7$ rows
(changing 0.5\% for pgSphere, not at all for the two B-trees) -- what the structures
predict, an 8-byte key with its tuple header against a bounding volume per GiST entry --
so extrapolating to Gaia DR3's $1.81\times10^9$ sources is a comparison of
\emph{deployments}: pgSphere answers cone searches and stores regions, \texttt{q3c\_join}
is what archives use for cross-matching (2.4 times faster than pgSphere at it,

\texttt{skycell} answers both from one, and that one is the smaller kind.

The memory column is the operational point: which cache regime a server is in is decided
by whether the index fits beside the heap's working set, and at DR3 scale a 64\,GiB
server holds \texttt{skycell}'s 38\,GiB index with room to spare while the
pgSphere-plus-Q3C pair needed for the same coverage wants 256\,GiB. That factor-four gap
is a procurement decision at these sizes, not a tuning one, and it lands exactly where
our cold-cache measurements put \texttt{skycell} furthest ahead: on the $5\times10^7$-row
corpus, warm \texttt{skycell} against cold pgSphere (the comparison a 64\,GiB archive
actually faces, since only the former's index is resident there) is one to two orders of
magnitude apart at 30\arcmin\ and beyond, and within 10\% at small radii where both are
memory-bound regardless.

intermediate hit rate rather than missing every time, and the true figure depends on
locality we have not measured at that scale -- but the direction and order of magnitude
hold: the difference between the two designs turns from percent to factors exactly when
the index outgrows the machine, the regime a $10^9$-row catalogue puts a server in. Four
further caveats: the extrapolation is linear and validated only over a factor five in row
count; it covers the positional index alone, dwarfed in a real archive by the table and
its other indexes; a partitioned deployment needs only its active partitions resident;
and since the two B-trees are the same size, the real saving is not needing the geometry
index at all, which rests on \texttt{skycell} answering the region queries pgSphere is
kept for (Sects.~\ref{sec:cones}, \ref{sec:otherops}).

\subsection{Cross-matching}
\label{sec:xmatch}
\label{sec:otherops}

Convex polygons of 0.05\degr--2\degr\ take a median 0.281\,ms on the Gaia corpus against
pgSphere's 0.767\,ms and Q3C's 1.864\,ms, and similarly on the designed corpus: a factor
2.7--4.4 either way, with pgSphere's mean and 95th percentile far above its median where
a polygon's bounding volume is a poor fit.

Cross-matching a user's uploaded target list against the catalogue is the operation the
Gaia archive lists among its server-side capabilities \citep{gaiaarchive1} and Q3C's own
speciality (\texttt{q3c\_join}), so it deserves the cone searches' protocol rather than a
single end-to-end run: getting that protocol right mattered more here than anywhere else
in this paper. At 50 million rows the catalogues and indexes are about 14\,GB against
2\,GB of \texttt{shared\_buffers}, so whichever method runs first on a block of probes
pays an I/O cost the others don't (a first version of this measurement cost
\texttt{skycell} a spurious factor ten by going first); each method is therefore warmed
on its own query immediately before being timed, in a block-paired, randomized-order
protocol, so what is compared is the work each does. At 50 million rows this gives
\texttt{q3c\_join} as the fastest established method by a factor 2.4 over pgSphere, and
\texttt{skycell}'s \texttt{LATERAL} form level with it (0.78--0.92 of its time, not
distinguishable) and 2.5--3.3 times faster than pgSphere; the fixed-slot join form is
level with Q3C at 1\arcsec\ but 35\% slower at 10\arcsec, where a fixed slot count fits
the covering less well.

Why level rather than better traces to the covering itself: the sky it scans, as a
multiple of the sky asked for, peaks around 105 near 0.25--1\arcsec\ (where the cost
model won't cut finer, since the extra ranges would cost more than the area saved) and
falls to 1.07 above 30\degr. A cross-match at 1\arcsec\ therefore does two orders of
magnitude more area work than the region requires and still draws level with
\texttt{q3c\_join}; the same index at degree scale, where the covering is within a third
of the region, wins outright.

We repeated this on the real corpus at the radii cross-matching actually uses --
optical work at $1$--$1.5\arcsec$, radio up to $5\arcsec$ (Table~\ref{tab:xmreal}; an
earlier $30\arcsec$ point was an association radius, not a cross-match one, and is
dropped). Over that range the \texttt{LATERAL} form is level with \texttt{q3c\_join}
(geometric mean 0.98 over twenty-four cells) and 3.0 times faster than pgSphere; the
fixed-slot form is the weaker of our two here (1.32 of \texttt{q3c\_join}) and degrades
further above these radii, a bound on that form rather than a general weakness. The claim
this supports is narrow: on the operation Q3C is built for, \texttt{skycell} is Q3C's
equal rather than its better, while being 2.5--3.3 times faster than pgSphere, with the
same index that answers the region queries of Sect.~\ref{sec:cones}.

Sect.~\ref{sec:phase} applies.

\paragraph{Estimates, plans and joins.}
\label{sec:joins}

A spatial predicate is rarely alone. We ran three shapes -- a cone with a catalogue cut,
the same joined to an observation table, and a three-way join -- through each method,
recording the estimate, the plan strategy and the time separately: skycell's estimate
advantage carries over (median error 1.15--1.88 at 30\arcmin--1\degr\ against 1.63--2.33
for Q3C and 2.50--3.00 for pgSphere), but the plans are the same. Across 135 queries at
1\arcmin--1\degr\ all three methods chose the same strategy for every query except one at
3\degr, where skycell's estimate produced a hash join 1.29 times faster than pgSphere's
nested loop; execution times are otherwise within noise. The honest summary: better
estimates are demonstrated, better plans and better join times are not -- an accurate
estimate is insurance against a query we did not write, and we have not shown that
insurance paying off on one we did.

\subsection{The cost model: its parameter, its input, and what it is worth}
\label{sec:calib}

Equation~(\ref{eq:cost}) has one free parameter, $c_{\rm range}$, and it need not be a
parameter at all: it is a ratio of two costs PostgreSQL already models, one more index
range (a B-tree descent, $(\lceil\log_2N\rceil+H+1)\cdot50\,c_{\rm op}$) against one
false-positive row (its index entry, heap tuple, the exact predicate, and its heap page
amortised over the rows sharing it):
\begin{equation}
  c_{\rm range} = \frac{(\lceil\log_2 N\rceil + H + 1)\,50\,c_{\rm op}}
    {c_{\rm tuple} + c_{\rm itup} + k\,c_{\rm op} + c_{\rm page}/n_{\rm pp}},
  \label{eq:crange}
\end{equation}
with $n_{\rm pp}=\mathrm{reltuples}/\mathrm{relpages}$. Every input is already at hand,
so \texttt{skycell.range\_cost} defaults to evaluating it, per-relation rather than
per-installation (116 on the catalogues at 120 rows/page; 93 on a wider-row ObsCore
relation at 54 rows/page). Placed in the same trials as the fixed constant it replaces,
the two are indistinguishable, because the cost curve is flat (sweeping over four decades
moves the median time under 25\% between 3 and 300): what the derivation buys is not
speed but that the parameter stops being a number someone has to choose. The order it
picks is likewise close to optimal (about 3\% against one order finer at 6\arcmin), for
the same reason -- the model does not need to be right, only to land in the flat region.

\label{sec:estimator}
The model's input, $\hat\rho$ from Eq.~(\ref{eq:rho}), was called unbiased in an earlier
version of this work -- true of positions resampled from a density map with no structure
below $0.11\degr$, but not of real Gaia DR3 positions. Table~\ref{tab:estimator} compares
$\hat\rho$ with $\rho$ counted from the same relation: good to about $\pm25\%$ on
ordinary sky, \emph{low by a factor 8--12} in a globular cluster core, \emph{high by a
factor 3.7} at the Galactic centre, as the histogram resolves a cluster while a query
sits inside it and averages it away once the query is larger (the failure
Sect.~\ref{sec:density} predicts, now measured on real positions rather than argued
about). The consequence is smaller than the error suggests: since $s^*\propto\sqrt\rho$,
an order of magnitude in $\rho$ is a factor three in cell size, and the cost curve is
flat across that -- the covering chosen in a cluster core, where $\hat\rho$ is wrong by
an order of magnitude, is within 1.09--1.43 of the best fixed order, no worse than where
the estimate is accurate. The estimator should be judged by the decision it produces, not
the number it reports.

The comparison with pgSphere confounds three things, which separate as follows on the
real Gaia corpus. \emph{Heap clustering} is a large absolute effect and almost no
differential one: unclustered rows cost 1.38--2.08 times more for \texttt{skycell} and
1.55--2.22 times more for pgSphere across $10\arcsec$--$1\degr$, but the ratio between
them barely moves (0.64 clustered against 0.60 unclustered at $1\degr$), so physically
ordered tables do not account for the comparison. \emph{Adaptive resolution} is worth a
great deal: against every fixed order 4--13, the penalty for choosing badly is
243--830$\times$, and the best fixed order moves from 12--13 at $10\arcsec$ to 7--8 at
$0.5\degr$, while the cost model lands within 1.02--1.58 of the best without knowing the
answer. \emph{The index representation} is isolated by comparing against Q3C instead,
since both are B-trees over an \texttt{int8} key and only the covering strategy differs
(Sect.~\ref{sec:cones}, with the caveat of Sect.~\ref{sec:scope}).
\label{sec:ablation}

\section{Inside a TAP service, and where the crossover is}
\label{sec:tap}

\paragraph{The service-level A/B.} A benchmark of index operations is not a benchmark of an archive. We ran the same build
inside \texttt{egernia} \citep{egernia}, a TAP 1.1 server, against its published
500\,096-row ObsCore corpus: one database holding both indexes, two otherwise identical
service processes differing only in how they translate \texttt{CONTAINS}, interleaved
rung by rung over six query classes at 1, 8 and 32 concurrent clients, three repetitions
each. Both targets pass the conformance gate and the cross-server agreement gate on all
eleven portable classes, with identical rows through both translations. The performance
result is a tie -- all 18 comparison cells fall inside the tie rule (throughput ratios
0.96--1.06) -- although at the database level \texttt{skycell} is 1.2--1.45 times
\emph{slower} per query on that corpus. Both facts share a cause: a cone over half a
million rows costs a fraction of a millisecond either way against roughly 10\,ms of CPU
in the service's own Python, so the database is 1--3\% of a request and a 0.08\,ms
difference in it cannot move throughput.

\paragraph{Where the crossover is.} That explanation makes a testable prediction. We built the same ObsCore-shaped relation
-- observations in groups of 128 products sharing a field centre, clustered by
collection and field, which is what makes a GiST bitmap scan so effective on this data --
at three sizes, and ran the same four cone classes against both indexes
(Table~\ref{tab:crossover}). The crossover is real but not a single number: for the cone
with catalogue cuts (Q07) and the degree-scale cone (Q06), \texttt{skycell} is ahead at
every size and pulls further ahead as the relation grows (a seventh of pgSphere's buffer
pages at Q06, a quarter at Q07); the empty cone (Q12) is level. The small-cone class
(Q05, 0.15\degr) we cannot pin down -- 2.16 times slower immediately after the build,
level (0.94) once thoroughly warm, and not reproducible on this host to better than a
factor of two -- but the deficit is at least localised, in execution (0.324\,ms against
0.161) rather than planning or the exact predicate.

\paragraph{When the index no longer fits in memory.}
\label{sec:pressure}
Section~\ref{sec:scale-memory} argues from index size alone that a host must reach a
point where pgSphere's index no longer stays in memory while \texttt{skycell}'s still
does; we tested the arithmetic directly. In a 3\,GiB container (768\,MB shared buffers)
holding a 22\,GB, 20.5-million-row ObsCore-shaped relation -- GiST index 1162\,MB
($1.51\times$ the buffer pool), \texttt{skycell} 439\,MB ($0.57\times$) -- a stream of
3500 uniform 2\degr\ cones (covering the sphere about once, needed to make the cache
matter at all) was run against each index in its own phase, server restarted between
phases, both phase orderings tried. \texttt{skycell} answers 4.2--4.8 times faster,
serving 53\% of its index accesses from the pool against pgSphere's 9\%. Two
qualifications: the 22\,GB heap alone takes 705--734\,MB of the pool in every phase, so
\emph{neither} index is actually resident -- what is measured is a smaller index winning
a contested pool, not a clean fits/doesn't-fit threshold -- and running both translations
in a single interleaved pass instead (the design we tried first, where each leaves the
shared heap pages warm for the other) puts the gap at $1.6\times$ rather than $4.2$.

\section{Discussion}
\label{sec:discussion}

The advantage is not universal, and stating where it stops is as informative as stating
where it holds. Warm, between 6\arcmin\ and 1\degr, \texttt{skycell} is indistinguishable
from pgSphere on one corpus and slightly slower at 6\arcmin\ on the other. On a
500\,000-row ObsCore relation it is slower; on the small-cone ObsCore class it is slower
in one cache regime and level in another, and we do not claim that row. Better row
estimates did not, on the join shapes we wrote, produce better plans. And every number
here comes from one machine and one storage device, with a density field standing in for
real catalogue positions except where Sects.~\ref{sec:xmatch} and~\ref{sec:estimator}
say otherwise.

What remains expensive is planning: a covering costs 0.015--0.12\,ms even cached against
0.006--0.008\,ms for a GiST predicate that needs no such step, the whole of
\texttt{skycell}'s disadvantage at 6\arcmin. We prototyped an SP-GiST operator class over
the cell hierarchy to remove this architecturally rather than amortise it, and found it
is not the clean fix it looks like on paper: the compression needed to keep the tree
compact costs correctness margin elsewhere, shrinking the duplicate-position tolerance by
roughly an order of magnitude. That prototype is exploratory and not part of the released
extension, so we report only the qualitative conclusion -- an index descent that avoids
planning ranges remains open, not solved.

The density synopsis is the other limit: an equi-depth histogram cannot see a cluster
smaller than one of its buckets, and raising the statistics target does not help, since a
denser region gets narrower buckets and the interpolation stays scale invariant. The area
guard bounds the damage; a custom \texttt{typanalyze} storing a multi-order count map
would estimate what the covering actually needs, and we have implemented one as an
option, but have no measurement showing it helps.

\section{Conclusions}

\texttt{skycell} keeps Q3C's compact integer key and B-tree while answering the region
queries pgSphere was built for, by treating the depth of a covering as a cost question
whose answer follows from the local source density and the price of an index range. The
result is a single index that holds its own against each established extension on the
workload the other one owns. Against pgSphere it is faster for cone searches at most
radii warm and at every radius cold, by a factor of up to 2.5, and answers convex
polygons 2.7--4.4 times faster. Against Q3C, at the cross-match Q3C is built for, it is
Q3C's equal and 2.5--3.3 times faster than pgSphere at the same operation. It gets there
with an index a third the size of pgSphere's -- 38\,GiB against 160\,GiB at Gaia DR3
scale for the pgSphere-plus-Q3C pair that covers the same ground, the difference between
a 64\,GiB server and a 256\,GiB one -- built thirty times faster, with row estimates
twice as accurate, and a cost model whose one parameter is derived from the relation's
own statistics rather than configured.

\texttt{skycell} also closes two gaps that neither established extension closes alone.
It speaks ADQL's own vocabulary as directly as pgSphere, with an operator form a planner
can answer from an index; and its stored regions read and write as IVOA STC-S text
itself, so an ObsCore \texttt{s\_region} column round-trips against an archive's own
text with no translation step. Because \texttt{skyregion} is one type tagged by kind
rather than a family of per-shape types, a single column holds circles and polygons
together -- exactly the case, a mixed-shape footprint column, that pgSphere cannot
represent in one column at all. Combined with a single compact index that serves both
point and region queries, this makes \texttt{skycell} a strong candidate for the
geometry layer of an IVOA TAP service, where ADQL compliance, STC-S storage and
mixed-shape footprints are what an archive already needs to provide, and where
Sect.~\ref{sec:tap} shows it dropping into a working TAP server without changing the
service's own behaviour.

The advantage is a property of the workload rather than a universal one, and scale
sharpens it rather than erasing it: raising the catalogue to 50 million rows widens the
lead for regions of 30\arcmin\ and above -- to a factor 3.2 at 1\degr\ cold -- while
cones of an arcminute and below stay level with pgSphere, because both methods touch a
handful of pages there at any table size and what is left is planning. That is also
where a small relation, or a TAP server whose own cost is dominated by Python, favours
pgSphere or leaves the choice immaterial. Choosing an index carefully matters when the
scan dominates; we have tried to say precisely which queries those are.
